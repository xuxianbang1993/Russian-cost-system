# ELSCBSSXT 产品需求文档（PRD）

> 本目录是**产品视角**的需求与功能规格说明，与 `docs/plans/`（开发时间线）和 `DEVELOPMENT_STRATEGY.md`（开发纪律）分工互补。

## 📐 目的

- **对上**：让产品/业务方快速理解"做什么 + 为什么做"
- **对下**：让开发/QA/新成员明确"做到什么程度算完"
- **对内**：沉淀业务决策与规则，避免口头共识随时间流失

## 🎯 读者指南

| 你是谁 | 建议阅读顺序 |
|-------|-----------|
| **产品/业务** | PRD-00 总览 → 选关心的模块 PRD |
| **新加入的开发** | PRD-00 → PRD-01 认证 → PRD-02 计算引擎 → PRD-04 工作台 → 对应功能 PRD |
| **QA** | 对应模块 PRD 的 §7 验收标准 |
| **测试用例编写** | PRD-02 黄金用例 + 各 PRD §7 |

### 🧭 核心设计哲学（v0.1.0）

**数据一致性模式：动态而非快照**
- 商品参数变更 → 历史测算的数字跟着变（Q7）
- 税率变更 → 历史测算用最新税率重算（Q9）
- 删除操作 → 硬删除（Q8）
- 取舍：v0.1.0 不做审计合规模式，简单优先；v1.0.0 再考虑"审计模式"支持历史锁定

**技术一致性**
- 防御纵深：所有数据访问 Server Action + Repository 双层 userId，不依赖 RLS 单层
- Server Component 默认，Client 下推到叶子
- Design Tokens 严格执行，禁止硬编码

## 📏 统一模板

每份 PRD 包含以下 9-10 节：

1. **需求背景**（WHY）— 业务痛点 + 产品价值
2. **用户场景**（WHO & WHEN）— 典型用户故事
3. **功能清单**（WHAT）— MoSCoW 优先级
4. **业务规则** — 财务红线、边界条件、异常路径
5. **交互细节** — 页面流程 + 关键 UI 描述
6. **数据模型** — 涉及的表 / Schema / 契约
7. **验收标准**（Definition of Done）— 可测试的断言
8. **非功能需求** — 性能 / 安全 / a11y / 兼容性
9. **依赖、约束与风险**
10. **相关资源** — 外部链接 / 实施计划 / Checkpoint

## 🔄 版本与更新

- PRD 文件名含模块名而不含版本号，版本迭代在文件内 `版本` 字段标记
- 重大业务规则变更应**先改 PRD，再改代码**（PRD 是合同）
- 每次 PR 若涉及业务逻辑变更，PR 描述应引用对应 PRD 的章节号

## 🚫 PRD 不应包含

- ❌ 代码实现细节（那是 `docs/plans/` 的职责）
- ❌ 具体的 commit / 测试命令（那是 DEVELOPMENT_STRATEGY 的职责）
- ❌ 已废弃的设计（应归档或删除，不要留"曾经考虑过"）
- ❌ 超过 10 层缩进的需求树（说明拆分粒度错了）
